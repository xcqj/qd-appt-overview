# 关键技术方案与取舍

> 每项按「问题 / 方案 / 验证 / 边界」四段写。所有数字来自 `qd-appt-docs` 仓 `test-evidence.md` 的实测记录，
> 复现脚本在 `qd-appt-backend/script/test/`。测试环境是**本机单机**（MySQL + Redis 同机），不是生产压测。
>
> 一句话原则：**机制说明职责，数字说明范围，边界说明不能外推的部分。**

---

## 1. 号源并发：三道防线各管一段

**问题**
同一时间点只有一个号源，并发下单必须恰好一单成交；Redis 不可用时也不能超卖。

**方案**
三道机制按顺序介入，职责互不替代：

| 层 | 机制 | 作用 | 失败时 |
|---|---|---|---|
| ① 缓存占位 | `SET NX` 写 `appt:slot:hold:<slotId>`，TTL = 支付时限 | 在进入数据库前挡掉绝大多数并发 | 已配置可关闭（降级为纯数据库） |
| ② 单柱 CAS | `UPDATE slot SET status='TAKEN' WHERE id=? AND status='AVAILABLE'`，同事务写台账与单据 | 保证单行状态只前进一步，影响行数 0 即失败 | 释放占位并返回 `SLOT_GONE` |
| ③ 唯一索引 | `UNIQUE(slot_id, active_flag)` | 兜住「同一号源只能有一张有效单」 | 数据库 1062 拒绝 |

占位释放用 Lua 脚本**比对 value 后删除**，避免误删其他请求的键；下单事务失败时占位与单据一起回滚。

**验证**（`test-evidence.md` §2、§3）

- 50 并发争抢同一号源：**成功 1 笔 / `SLOT_GONE` 49 笔**，该号源有效单恰 1 行，断言 `PASS=14 FAIL=0`。
- 摘除防线① 的对照实验（`--appt.slot-hold.enabled=false` + `SKIP_HOLD=1`）：**仍 1 笔成交 / 49 笔被数据库 CAS 拒绝**，且占位键 `EXISTS=0`。
- 同一 `Idempotency-Key` 连续两次提交：两次均返回成功，第二次 `duplicate=true`，库中仅 1 单。

**边界**
- 50 并发是本机单机脚本的规模，不能外推为任意并发度下的证明，也不是生产压测。
- 对照实验证明的是「关掉缓存占位后数据库条件更新仍能挡住」，**不是**并发一致性验证；也没有做「关掉唯一索引」的实验（会破坏数据，不做）。
- 因此本项目的结论是「三层各有职责、任一层失效仍有下一层」，**不是**「绝对不超卖」。

## 2. 限购：先串行化账号，再在锁内精查

**问题**
黄牛用同一就诊人批量占号；同一患者同日跨科室重复下单。单纯「先查后插」在并发下必然穿透。

**方案**
- **口径**：同一就诊人同一就诊日 1 单，**跨院区共享额度**（ADR-0001，2026-10-23 起生效）；旧口径（同医生同日 / 同时段 / 最多 3 单）废弃。
- **实现**：下单前对 `sys_user` 的账号行做 `SELECT ... FOR UPDATE`，把同一账号的并发下单串行化；锁内按三条规则精查并返回精确错误码（如 `LIMIT_PATIENT_DAY`），最后仍由复合唯一索引兜底。
- **为什么锁的是账号行**：限购按「账号 + 就诊人」统计，锁住账号行才能让同一账号的统计互斥；只锁单行、不 JOIN，不构成跨模块联表。

**验证**（`test-evidence.md` §2）
- 同日跨科室下单被 `LIMIT_PATIENT_DAY` 拦下；不同就诊日各下 1 单均成功。
- 同一幂等键双击：第二次 `duplicate=true`，库中仅 1 单。
- 该轮脚本 `PASS=11 FAIL=0`（11 条断言；原「限购三条」合并为一条规则后由 14 降至 11）。

**边界**
- 只解决**同一账号**的并发；跨账号争抢同一号源由第 1 项的号源 CAS 负责。
- 锁是数据库行锁，持有时间覆盖锁内查询；高并发下会放大同账号请求的排队，属预期代价。
- 黑名单判定必须在同一把账号锁内调用（建名单走独立事务），否则会出现「刚被拉黑还能下单」的窗口。

## 3. 停诊：两段式 + 一条登记一个批号

**问题**
停诊一旦直接退号退款，误操作与重复提交会放大影响面：批量回池、批量退款、批量通知都不可逆。

**方案**
- **登记（第一段）**：只落一条 `PENDING` 记录，**不动号源、不退款、不发通知**；同范围重复登记返回原批号（`duplicate=true`）。
- **处理（第二段）**：按登记批量执行——排班置 `SUSPENDED`、可约号源置 `SUSPENDED`、已预约单转 `CANCELED_PASSIVE`（`active_flag=NULL`）、已支付单生成退款单、发站内信、登记置 `HANDLED`；已签到单**跳过**（不参与批量退号）。
- **幂等**：一条登记一个批号；处理按批号 + 状态 CAS，重复处理返回 `handled=false`，不会重复退款。
- **范围编码**：`scope_type + scope_value` 由统一构造器生成（ADR-0004；曾因手工拼串两次串号）。原「按日拆 N 条共用批号」因批号唯一约束不可实现，已废止。

**验证**（`test-evidence.md` §9，脚本 `s6b_suspend_blacklist.sh`）
- `PASS=25 FAIL=0`；摘要「排班 1 / 号源 2 / 被动退号 1 / 退款 1 / 跳过已签到 1」。
- 同范围重复登记返回同 `suspendId` / 同批号，不新建行；重复处理 `handled=false` 且退款单仍 1 条。
- 已签到单保持 `SIGNED`、其号源保持 `TAKEN`；余量预置 5，停掉 1 个可约号源后为 4。

**边界**
- 停诊是**批量不可逆**操作，处理前没有二次确认之外的兜底（后台按钮层面），演示时建议先小范围登记。
- 已签到单不回退：业务上视为已履约，需人工处理。
- 真实渠道退款未验证（Mock 渠道）。

## 4. 余量查询：一次聚合 + 有守卫的缓存增量

**问题**
排班页要显示「每位医生 × 每个午别」的可约余量。直觉写法是每位医生两次 `COUNT`，20 位医生就是一屏 40 次查询，随医生数线性增长。

**方案**
- **读取**：一条 `GROUP BY schedule_id, period` 的 `COUNT` 聚合，走 `idx_slot_schedule_status`；单屏 SQL 固定 2～3 条，**与医生数无关**。
- **缓存**：`appt:remain:<scheduleId>:<period>`，`MGET` 批量读，未命中回源聚合后 `SETNX` 回填（TTL 600s）。
- **写路径唯一入口**：号源状态变更在事务 `afterCommit` 经 Lua `EXISTS → INCRBY ±1`；**键不存在就不创建**，避免缓存里出现「没有来源的 0」。
- **增量语义按目标状态分支**：可约→已占 `−1`、已占→可约 `+1`、已占→已过期 `0`（过期不等于回池）。写反会让余量与数据库长期漂移。
- **可关闭**：`appt.remain.cache=redis|db`，db 模式读写两侧都旁路缓存。

**验证**（`test-evidence.md` §7）
- 100 并发 × 1000 样本 × 3 轮（curl 进程开销计入，取中位）：缓存 p95 **9.3 ms**（QPS ≈1050）、直查 p95 **10.6 ms**（QPS ≈1160）；命中率 100%。
- 单屏 SQL：冷启动 3 条 / 缓存命中 2 条 / `db` 模式 3 条，均不随医生数增长。
- 一致性：**顺序循环** 1000 次「挂号 → 超时关单」后逐键比对，缓存与数据库差值 0，断言 `PASS=11 FAIL=0`。

**边界**
- 延迟差异只有 14%，且 QPS 略低；文档结论是「默认保持缓存」，**不是**「缓存显著更快」。收益主要在少查数据库，不在压测数字。
- 一致性检查是**串行**循环，不是并发一致性验证；写路径依赖事务提交后的回调，极端情况下存在秒级窗口（TTL 600s 内收敛）。
- 对已存在排班「补号」时缓存可能滞后 ≤600s，属显示侧可接受。

## 5. 支付回调：先落库去重，再异步入账

**问题**
渠道会重复回调、乱序回调、在订单关闭后才回调。直接「回调即改单」会重复入账、状态回退，或出现「钱到了号没了」。

**方案**
- **验签** → 回调 **append-only 落库**（含去重键）→ **立即 ack** → **异步入账**（有界线程池 + 独立事务）。
- 重复回调命中唯一键，标记 `duplicate=true`，不二次入账。
- **关单后到达的回调**：自动建退款单（或走重复支付退款分支），不回退挂号单状态。
- **退款回调**：CAS 置 `REFUNDED`，并把挂号单结算状态推进到 `REFUNDED`。
- **超时关单**：定时巡检「近过期查单 + 到期关单」，三步 CAS + `RELEASE` 台账 + 释放占位，关单与回补同一事务。
- Mock 渠道的 `tradeNo` 由支付单号确定性派生，保证回调去重键稳定非空。

**验证**（`test-evidence.md` §5）
- 同一支付单回调重复 3 次：**入账 1 次**、回调记录 1 条、2 次 `duplicate=true`；脚本 `PASS=20`（后续回归为 `PASS=21`）。
- 关单 → 号源回补 → 可被再次预约；关单后到达的回调自动走退款分支。
- 并发 5 次关单仅 1 次生效；篡改签名的回调被拒绝。

**边界**
- 全部基于 Mock 渠道；真实渠道的签名算法、证书轮换、对账文件未验证。
- 异步入账是**最终一致**（秒级），不是强一致；线程池有界，极端堆积时会延迟入账但仍可重放。
- 「钱到了号没了」只做到自动退款，不做到「保住号源」——号源已被他人占用时无法回滚。

## 6. 这些数字不能说明什么

- 全部为**本机单机**脚本 / 配置开关对照 / 手工验收，不是生产压测，也不是容量规划依据。
- 并发用例的规模是 50（下单）与 100（读取），没有做过千级并发与长稳测试。
- 缓存对比的差异（14%）在单机噪声范围内，结论是「保持默认」，不代表普遍性能优势。
- 对账、发布、回滚的耗时是**演示环境**数字，与机器规格、镜像缓存强相关。
- 没有做故障注入（Redis 宕机、MySQL 主从切换、网络分区）；只有「关掉缓存占位」这一种降级路径被实测。
